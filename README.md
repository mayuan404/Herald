# Herald

把安卓手机的通知（短信、微信、验证码…）直接送到 Mac 菜单栏，**不经过任何服务器**。
顺带内置 TOTP 验证器（Google Authenticator 那类），验证码在 Mac 上生成。

## 为什么不用 KDE Connect

KDE Connect 依赖局域网 UDP 广播 + 直连，而很多 Wi-Fi 做了三层隔离（AP isolation），
手机和 Mac 明明在同一个 SSID 也互相不可见。Herald 走 **蓝牙 BLE**，
不经过 IP 网络，隔离与否都不影响。

## 架构

```
安卓：NotificationListenerService ──► BLE GATT server（广播 + 通知特性）
                                   └─► TCP 127.0.0.1:8765（adb reverse 联调用）
Mac：菜单栏 App（CoreBluetooth central）──► 通知列表 / 横幅 / 一键复制验证码
                                      └─► TOTP 生成器（本地）
```

- 数据格式：每行一个 JSON（`pkg/app/title/text/time`），\n 分隔；
- 不落盘、不上传，Mac 端只在本地保留最近 100 条；
- 手机端可按包名白名单过滤，避免被无关推送刷屏。

## 安装

### Mac 端

```bash
cd mac && ./build.sh
# 生成并安装到 ~/Applications/Herald.app
open ~/Applications/Herald.app
```

首次启动会请求「蓝牙」权限；菜单栏出现手机图标即表示在扫描。

### 安卓端（小米 14 / HyperOS）

1. 从 [Releases](https://github.com/mayuan404/Herald/releases) 下载 `Herald-0.2.0.apk`
   （或在本仓库 Actions 页面下载 `herald-apk` 产物）；
2. 安装后打开 Herald：
   - 点「授予通知读取权限」→ 在系统列表里勾选 Herald；
   - 点「启动后台服务」；
3. 省电设置（关键，否则后台会被杀）：
   - 设置 → 应用设置 → 应用管理 → Herald → 省电策略 → **无限制**
   - 设置 → 应用设置 → 应用管理 → Herald → 自启动 → 允许
   - 最近任务里给 Herald 加锁。

### 联调（没有蓝牙时）

```bash
adb reverse tcp:8765 tcp:8765
```

手机端只要服务在跑，就会自动走 TCP 连到 Mac。

## 验证器（TOTP）

Mac 端「验证器」页 →「添加验证器…」，粘贴：

- `otpauth://totp/Issuer:name?secret=BASE32&digits=6&period=30`，或
- 直接粘贴 Base32 密钥。

Google Authenticator 本身不导出，需要手动录入一次；或者之前用 Aegis 等能导出二维码的工具。

## 图标

`assets/icon-1024.png` 是唯一源文件，`assets/AppIcon.icns` 与
`android/app/src/main/res/mipmap-*/ic_launcher.png` 都由它生成，两端视觉一致。

## 已知限制

- BLE 单包 180 字节切片，长通知会分片，Mac 端按 `\n` 重组；
- 微信通知的内容取决于手机端「显示消息详情」是否打开；
- HyperOS 对后台蓝牙广播限制较严，若长时间收不到，重启一次服务。

### 0.1.1 的稳定性改动（针对「连上 30 秒就断」，0.2.0 沿用）

- **回执改成写无响应**：ACK 不再占用 ATT 事务，避免「对端没回 Write Response → 30 秒后
  `CBInternalErrorDomain Code=13` 整条链路被断开」的循环（日志里出现过 1000+ 次）；
- **分片发送加流控**：每片等 `onNotificationSent` 回调再发下一片，长通知不再丢片；
- **重连指数退避**（1/2/4/8/16/30 秒），不再「断了立刻连、3 秒连不上就 cancel+rescan」；
- **看门狗从 60 秒放宽到 10 分钟**（手机息屏时本来就没通知，之前的阈值把健康连接也掐了）；
- **不再自动 `createBond()`**：配对状态机与 MIUI 的冲突是「已连接/已保存」错乱的来源之一；
- **补上写入完成/失败的日志**，下次排查能直接看到是哪一次 ATT 操作没回来。

## 应用层加密（配对码）

**安全边界就是这一层**：链路层配对（bond）在 MIUI 上不可靠，而且只是「对端是谁」的弱认证，
不改变「同频段可嗅探」的事实，所以不把它当安全依据。

1. Mac 菜单栏 → **配对码** → 「复制」；
2. 手机 Herald → 粘贴到「配对码」输入框 → **保存配对码**；
3. 两端用 `SHA-256(code + "|PhoneBridge|v1")` 派生 32 字节密钥，消息体用 **AES-256-GCM**（12 字节随机 nonce）加密，
   外层是 `E1:` + base64(nonce‖密文‖tag)；
4. 配对码不一致时 Mac 顶部会显示「配对码不一致」，消息不会被渲染。

规则（0.1.1 起）：

- **手机端没有配对码就不发送**（不再退回明文）；
- **Mac 端丢弃一切非 `E1:` 明文**，并在菜单栏显示「已拦截明文报文」；
- 同一个 `msgId` 只处理一次（防重放，窗口 500 条）；手机端重发会命中，补一个 ACK 后丢弃。

## 安全模型

1. **应用层认证加密**：AES-256-GCM，密钥只由配对码派生（16 位 base32，约 80 bit 熵，
   首次启动自动生成，可随时重置）。没有配对码的第三方即使连上 BLE、订阅了通知，
   拿到的也只是密文；伪造的明文会被直接丢弃。
2. **链路层配对是可选项**：不再在连接瞬间 `createBond()`（这正是 MIUI 上状态错乱的来源）。
   已配对的设备继续可用；没配对也不影响功能，只是少一层「设备身份」确认。
3. **只用 BLE，不连 IP 网络**：数据不经过路由器、服务器，也不受 Wi-Fi 隔离影响。
4. **TCP 调试口只绑回环**：`127.0.0.1:8765`（配合 `adb reverse`），不监听局域网，
   并且同样只接受 `E1:` 密文。
5. **不落盘、不上传**：Mac 端只在 `~/Library/Application Support/Herald/` 保存最近 100 条通知
   与验证器密钥（目录 0700，密钥文件不加密）。
6. **可裁剪**：手机端可以只选要转发的 App；不选则全部转发。

### 这套机制的边界（如实说明）

- 配对码存在 Mac 的 `UserDefaults` 与手机 `SharedPreferences` 里，**同机其他进程/拿到备份的人可以读**；
  这不是防本机恶意软件的方案。
- BLE 链路本身不加密，**通知的「有/没有、多大、什么时候」这类元数据**同频段可见（内容不可见）。
- 没有在线尝试次数限制；80 bit 熵的配对码按目前的 BLE 速率不可能在线爆破，但**不要把配对码换成人手输入的短口令**。
- 重放防护是「最近 500 个 msgId」窗口：能挡住近期的重复投递，挡不住很久以后重放一条旧密文（影响仅限于再次显示旧通知）。
- 单机单手机：没有设备白名单，任何持有配对码的设备都能冒充手机（配对码即身份）。

## 验证器：从 Google Authenticator 迁移

Google Authenticator（GA）**没有导出文件**，它的「转移账号」是**二维码**。做法：

1. 手机上打开 GA → 右上角 ⋮ → **转移账号** → **导出账号**；
2. 勾选要迁移的账号 → **导出**，GA 会显示一个（或分批多个）二维码；
3. **截图**（每个二维码各截一张；GA 一批最多 20 个账号，10 多个通常一张就够）；
4. 把截图传到 Mac（隔空投送 / 微信文件传输助手都行）；
5. Mac 菜单栏图标 → **验证器** 页 → **「导入验证器…」** → 选中截图；
6. 识别成功会提示「已导入 N 个验证器账户」，之后每 30 秒刷新一次验证码，点一下复制。

识别失败时：

- 确认截的是 GA 的二维码页面（不是列表页）；
- 二维码被截断/缩放模糊会识别不出，尽量原图、别裁掉四周白边；
- GA 分批显示多个二维码时，把每张都选上（导入对话框支持多选）。

## 通知列表

- **按 App 分组，默认全部折叠**，点组标题展开；
- 每组**最多保留 5 条**，超出自动丢最老的（这是提示工具，不是收件箱）；
- 每条消息右上角 `×` 可单条删除；
- 收到带验证码的消息时，点行内「复制」或整行即可复制（有意不做自动写剪贴板，避免覆盖你正在复制的东西）；
- 手机端「选择要转发的 App」可只转发短信/微信，不选则全部转发。
